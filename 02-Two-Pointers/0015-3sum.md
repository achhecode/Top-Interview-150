## 1. Problem in Simple Words

**Given:** an integer array `nums`.

**Required:** return all unique triplets `[nums[i], nums[j], nums[k]]` (distinct indices) whose values sum to `0`. No duplicate triplets in the output.

**Constraints that matter:**
- `3 <= nums.length <= 3000` — n² (≈9,000,000) is comfortably fast enough; n³ (≈2.7×10^10) is not. This constraint is the hint: the optimal approach is O(n²), not brute-force O(n³).
- `-10^5 <= nums[i] <= 10^5` — values fit safely in `int`, but summing three of them (max ~3×10^5) is still fine for `int`; no overflow risk here, unlike problems that multiply values.

## 2. Recognition Signals

- "Find all triplets/pairs that sum to a target" + "no duplicates in the result" → classic Two Sum / Two Sum II variant fixed at one index.
- The need to dedupe combinations (not just find one answer) strongly suggests **sort first**, since duplicates become adjacent and target values become easy to skip.
- n is small enough (≤3000) that O(n²) is clearly intended, ruling out a naive triple-nested loop.
- "Fix one element, solve a two-sum on the rest" is the trigger phrase — this is the **Two Pointers after Sorting** pattern.

## 3. Core Idea

Sort the array. Fix each element `nums[i]` as the anchor for a target, then find two other numbers in the remaining sorted subarray `(i, n-1]` that sum to `-nums[i]`, using two pointers moving inward from both ends.

**Why it's correct:** once sorted, for a fixed left pointer sum `nums[left] + nums[right]`, increasing `left` only increases the sum and increasing/decreasing `right` only decreases it monotonically. So instead of checking all pairs, we can move the pointer that gets us closer to the target — this eliminates the need to check pairs we can mathematically rule out.

**Invariant:** at every step, all triplets with anchor `< i` have already been fully explored and recorded; within the two-pointer scan for anchor `i`, all pairs `(left', right')` with `left' < left` (or symmetric ones already skipped) have been ruled out as too small or too large relative to the target.

## 4. Approach 1 — Brute Force

1. Try every triplet of indices `i < j < k`.
2. If `nums[i] + nums[j] + nums[k] == 0`, add the triplet (as a sorted list) to a `Set` to dedupe.
3. Return the set as a list.

```java
public List<List<Integer>> threeSumBruteForce(int[] nums) {
    Set<List<Integer>> uniqueTriplets = new HashSet<>();
    int n = nums.length;
    for (int i = 0; i < n; i++) {
        for (int j = i + 1; j < n; j++) {
            for (int k = j + 1; k < n; k++) {
                if (nums[i] + nums[j] + nums[k] == 0) {
                    List<Integer> triplet = Arrays.asList(nums[i], nums[j], nums[k]);
                    triplet.sort(null);
                    uniqueTriplets.add(triplet);
                }
            }
        }
    }
    return new ArrayList<>(uniqueTriplets);
}
```

**Time:** O(n³) — three nested loops.
**Space:** O(n) auxiliary for the dedup set (plus output).

This is not optimal: with `n = 3000`, n³ ≈ 2.7×10^10 operations, far too slow within interview or judge time limits. It also leans on a `Set<List<Integer>>` for dedup rather than solving the duplicate problem algorithmically, which is a weaker demonstration of pattern recognition.

## 5. Approach 2 — Optimized (Sort + Two Pointers)

1. Sort `nums` ascending.
2. Iterate `i` from `0` to `n - 3`, treating `nums[i]` as the smallest element of the triplet.
3. Skip `i` if `nums[i] == nums[i - 1]` (i > 0) to avoid duplicate anchors.
4. If `nums[i] > 0`, break — the smallest remaining element is positive, so no triplet can sum to zero.
5. Set `left = i + 1`, `right = n - 1`. While `left < right`:
   - Compute `sum = nums[i] + nums[left] + nums[right]`.
   - If `sum == 0`: record the triplet, then advance `left` and retreat `right` past any duplicate values, and move both pointers inward by one.
   - If `sum < 0`: increment `left` (need a bigger sum).
   - If `sum > 0`: decrement `right` (need a smaller sum).
6. Return the collected triplets.

```java
public List<List<Integer>> threeSum(int[] nums) {
    Arrays.sort(nums);
    List<List<Integer>> result = new ArrayList<>();
    int n = nums.length;

    for (int i = 0; i < n - 2; i++) {
        if (nums[i] > 0) {
            break; // smallest value is positive -> no zero-sum triplet possible
        }
        if (i > 0 && nums[i] == nums[i - 1]) {
            continue; // skip duplicate anchor
        }

        int left = i + 1;
        int right = n - 1;

        while (left < right) {
            int sum = nums[i] + nums[left] + nums[right];
            if (sum == 0) {
                result.add(Arrays.asList(nums[i], nums[left], nums[right]));
                left++;
                right--;
                while (left < right && nums[left] == nums[left - 1]) {
                    left++;
                }
                while (left < right && nums[right] == nums[right + 1]) {
                    right--;
                }
            } else if (sum < 0) {
                left++;
            } else {
                right--;
            }
        }
    }

    return result;
}
```

**Time:** O(n²) — O(n log n) for sorting, then O(n) anchors each driving an O(n) two-pointer scan.
**Space:** O(1) auxiliary (ignoring the output list and the space used by `Arrays.sort` for primitives, which is O(log n) for its internal quicksort recursion).

This is optimal for this problem: any correct solution must examine at least Ω(n²) pairs in the worst case (there's no sub-quadratic known approach for general 3-sum), so O(n²) time with O(1) extra space is the standard best-known trade-off.

## 6. Dry Run

`nums = [-1, 0, 1, 2, -1, -4]` → sorted: `[-4, -1, -1, 0, 1, 2]`

| i (nums[i]) | left, right | nums[left]+nums[right] | sum | action |
|---|---|---|---|---|
| 0 (-4) | 1,5 (-1,2) | 1 | -3 | sum<0 → left++ |
| 0 (-4) | 2,5 (-1,2) | 1 | -3 | sum<0 → left++ |
| 0 (-4) | 3,5 (0,2) | 2 | -2 | sum<0 → left++ |
| 0 (-4) | 4,5 (1,2) | 3 | -1 | sum<0 → left++ → left==right, stop |
| 1 (-1) | 2,5 (-1,2) | 1 | 0 | **found [-1,-1,2]**; left→3, right→4 |
| 1 (-1) | 3,4 (0,1) | 1 | 0 | **found [-1,0,1]**; left→4, right→3, loop ends |
| 2 (-1) | — | — | — | `nums[2]==nums[1]` → skip (duplicate anchor) |
| 3 (0) | 4,5 (1,2) | 3 | 3 | sum>0 → right-- → left==right, stop |

Exit: loop ends when `i` reaches `n - 2`. Final answer: `[[-1,-1,2], [-1,0,1]]`, matching the example.

## 7. Complexity Summary

| Approach | Time | Space | Notes |
|---|---|---|---|
| Brute Force | O(n³) | O(n) aux (dedup set) | Too slow for n=3000; relies on hashing to dedupe |
| Sort + Two Pointers | O(n²) | O(1) aux | O(n log n) sort dominated by O(n²) scan; output not counted as aux space |

## 8. Edge Cases

| Case | Why it is tricky | How the code handles it |
|---|---|---|
| `n < 3` | No triplet possible | Constraint guarantees `n >= 3`, but loop bound `i < n - 2` naturally yields zero iterations if it weren't |
| All zeros `[0,0,0]` | Must return exactly one triplet, not zero or many | Duplicate-skipping logic after a match collapses repeats into a single `[0,0,0]` |
| All positive / all negative | No zero-sum triplet exists | Early `break` when `nums[i] > 0`; symmetric case naturally yields no match since two pointers can't balance to zero |
| Many duplicate values | Risk of duplicate triplets in output | Anchor dedup (`nums[i]==nums[i-1]`) plus post-match dedup for `left`/`right` |
| Values at extremes (`-10^5`, `10^5`) | Sum of three could look like overflow risk | Max magnitude sum is ~3×10^5, well within `int` range (±2.1×10^9), so no overflow |
| Exactly one valid triplet mixed with non-matching noise | Two-pointer must not stop early or skip past the match | `left < right` loop condition ensures every viable pair is inspected until pointers cross |

## 9. Java Notes

- `Arrays.sort(int[])` uses a dual-pivot quicksort for primitives — O(n log n) average, O(log n) extra stack space; this differs from `Arrays.sort(Object[])`, which uses TimSort with O(n) space. Since `nums` is `int[]`, the primitive sort applies.
- `Arrays.asList(int, int, int)` here resolves to `Arrays.asList(Integer, Integer, Integer)` via autoboxing, producing a fixed-size `List<Integer>` — fine for read-only output, but it would throw `UnsupportedOperationException` on `add`/`remove`.
- No `Integer.MIN_VALUE`/overflow concerns for this problem's value range, but it's worth noting explicitly in an interview since summing values is a classic place overflow bugs hide.
- `left < right` as the inner loop guard (rather than `left <= right`) is essential — at `left == right` the same element would be reused, violating the "distinct indices" requirement.

## 10. Common Mistakes

- Forgetting to skip duplicate anchors (`nums[i] == nums[i-1]`) → produces duplicate triplets in the output. Fix: `continue` when the anchor repeats a previous one.
- Skipping duplicates *before* checking `i == 0`, causing an `ArrayIndexOutOfBoundsException` or wrongly skipping the first valid anchor. Fix: guard with `i > 0 &&`.
- Moving `left`/`right` inside the match branch but forgetting the inner `while` de-dup loops, leaving duplicate `[-1,-1,2]`-style triplets when multiple equal values exist at the pointers. Fix: advance past equal neighbors after recording a match, not just once.
- Using `Set<List<Integer>>` (or string-based keys) to dedupe instead of the sort-based skip logic — works but is O(n) slower per insertion and misses the point of the pattern in an interview.

## 11. Interview Takeaway

- **Trigger sentence:** "Sum-to-target over triplets/pairs with dedup requirement + small-enough n → sort, fix one, two-pointer the rest."
- **90-second explanation:** "I sort the array so duplicates become adjacent and two-pointer scanning works. For each index `i` as the smallest of the triplet, I look for two numbers after it that cancel out `nums[i]` using a left pointer starting right after `i` and a right pointer at the end. If the three-sum is too small I move left up, if too big I move right down, if it's zero I record it and then skip past any duplicate values on both sides before continuing. I skip duplicate anchors the same way, and I break early once `nums[i]` itself is positive, since nothing after it can bring the sum back to zero."

## 12. Recall Questions

**Q:** Why does sorting the array first make the two-pointer scan valid?
**A:** Because in a sorted array, moving the left pointer right only increases the pair sum and moving the right pointer left only decreases it — the sum changes monotonically, so you can always tell which pointer to move to approach the target instead of checking every pair.

**Q:** Why is it safe to `break` out of the outer loop once `nums[i] > 0`?
**A:** The array is sorted, so if the smallest candidate for the triplet is already positive, every remaining triplet formed from it and larger numbers will also be positive and can't sum to zero.

**Q:** Why do we need two separate duplicate-skipping mechanisms (for `i` and for `left`/`right`)?
**A:** Skipping duplicate anchors prevents the same starting value from generating the same triplet set twice across outer-loop iterations; skipping duplicate `left`/`right` values after a match prevents the same triplet from being recorded multiple times within a single anchor's two-pointer scan.

**Q:** Why does the loop condition use `left < right` rather than `left <= right`?
**A:** The three indices must be distinct; allowing `left == right` would let the same array element be counted twice in one triplet.

**Q:** What would go wrong if we didn't sort the array first?
**A:** Without sorting, there's no monotonic relationship to exploit, so you couldn't decide which pointer to move — you'd be back to checking most pairs explicitly, losing the O(n²) guarantee and the easy duplicate-adjacency property.

**Q:** Why doesn't this problem need a hash-based dedup structure like `Set<List<Integer>>`?
**A:** Sorting already groups equal values together, so duplicates can be skipped in constant extra work per skip by comparing adjacent elements, avoiding the overhead and O(n) auxiliary space of a hash-based set.

## 13. Final Code

```java
import java.util.*;

class Solution {
    public List<List<Integer>> threeSum(int[] nums) {
        Arrays.sort(nums);
        List<List<Integer>> result = new ArrayList<>();
        int n = nums.length;

        for (int i = 0; i < n - 2; i++) {
            if (nums[i] > 0) {
                break;
            }
            if (i > 0 && nums[i] == nums[i - 1]) {
                continue;
            }

            int left = i + 1;
            int right = n - 1;

            while (left < right) {
                int sum = nums[i] + nums[left] + nums[right];
                if (sum == 0) {
                    result.add(Arrays.asList(nums[i], nums[left], nums[right]));
                    left++;
                    right--;
                    while (left < right && nums[left] == nums[left - 1]) {
                        left++;
                    }
                    while (left < right && nums[right] == nums[right + 1]) {
                        right--;
                    }
                } else if (sum < 0) {
                    left++;
                } else {
                    right--;
                }
            }
        }

        return result;
    }
}
```
